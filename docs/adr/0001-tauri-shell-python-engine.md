# Tauri shell + single Python Engine over localhost HTTP

Status: accepted (2026-08-25)

Readily needs a Mac-first shell that reaches the Python TTS ecosystem (where the models are), stays light on a base M1 8GB shared with a loaded model, and keeps Windows/Linux possible without a rewrite. We chose **Tauri** with a **React + Vite + TypeScript** frontend, **Bun** as the JS runtime/package manager (not Node), and a **single Python Engine sidecar** hosting both model backends — **mlx-audio** (expressive tier: Chatterbox, Qwen3-TTS) and **onnxruntime** (fast tier: Supertonic, Kokoro, Pocket TTS) — behind one internal API.

## The decisions

1. **Shell: Tauri, not Electron or SwiftUI.** RAM/disk argument is decisive on the 8GB floor. SwiftUI would lock us to mlx-audio-swift's lagging catalog and kill cross-platform. Electron stays the cheap escape hatch: the frontend, Engine, and uv strategy port to it nearly unchanged if Tauri proves unworkable. Accepted cost: some Rust in the core; a fully native feel is unreachable.
2. **One Engine process, not two lanes** (embedded sherpa-onnx + MLX sidecar). One process to spawn/supervise, one lane in the catalog manifest; the fast tier still runs (kokoro-onnx is a 21MB wheel). Embedding sherpa-onnx later is additive, not a rewrite — do it only if first-run friction is measured, not assumed.
3. **Engine owns the model lifecycle**: download, hash-verify, list, delete, load/unload — `huggingface_hub` gives resumable downloads for free, and the Engine is the models directory's only consumer. The Rust core stays a thin supervisor: spawn/health/restart, first-run provisioning, window chrome. The security pipeline's model-hash-verification rules target the Engine.
4. **Wire: localhost HTTP + SSE, token-guarded.** Engine binds `127.0.0.1:<random port>` with a bearer token generated by the Rust core at spawn; the webview calls it directly. OpenAI-compatible `POST /v1/audio/speech` where it maps; custom routes for catalog/playback; SSE for progress and playback events. Independently curl-able — the Engine is testable without the app.
5. **Audio plays outside the webview.** Web Audio in WKWebView is fine on macOS but a documented minefield on Linux/WebKitGTK; keeping the audio device in the Engine or Rust core makes gaplessness shell-independent. Which of the two owns it — and the whole pipeline (chunking, lookahead, scheduling, cache) — is [ADR 0002](0002-chunking-playback-pipeline.md)'s decision, not this one.
6. **Distribution: uv-provisioned Engine.** The .app ships no Python; first run pulls a pinned interpreter + wheels via a bundled `uv`. Offline install is impossible — acceptable, since a TTS app with no downloaded models is a paperweight anyway — and the PyInstaller notarization slog disappears.

## Consequences

- Two-language core (Rust supervisor + Python Engine); the frontend/product logic stays TypeScript.
- History/storage ownership is deliberately **not** decided here ([ADR 0004](0004-engine-owned-sqlite-flac-storage.md)); nothing above forecloses it.
- Intel Macs are out: no MLX wheels exist for x86_64-darwin, and the shell choice doesn't change that.
- The risky seams are sidecar spawn + uv provisioning, both backends behind the one API, and out-of-webview playback. A measured TTFA or RAM failure at any of them reopens this ADR.
